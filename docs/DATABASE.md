# Database

PostgreSQL, accessed only through Prisma. 33 tables and 19 enums in `prisma/schema.prisma`; the initial migration is `prisma/migrations/0_init/migration.sql`.

## Conventions

- **Primary keys** are `uuid` generated by the database default, never by an application counter. Foreign keys carry `@db.Uuid`.
- **Timestamps** are `TIMESTAMPTZ(6)` — every `DateTime` field in the schema carries `@db.Timestamptz(6)`, so PostgreSQL stores an instant rather than a wall clock that depends on the server's `timezone` setting. `createdAt` is defaulted and `updatedAt` is maintained by Prisma. Values are written and read in UTC; Rwanda is UTC+2 with no daylight saving, and local display happens in the client through `formatDateTime`, never by storing shifted values.
- **Money** is `Decimal`: `Decimal(12,2)` for payments and pricing, `Decimal(14,2)` for balances that accumulate. Amounts cross the API as strings and are computed as integer minor units (`packages/validation/src/money.ts`, 1 RWF = 100 centimes). No JavaScript float arithmetic touches an amount.
- **Currency** is stored per row with default `RWF` rather than assumed from context.
- **Rates** are basis points (`commissionRateBps`, `platformFeeBps`) so a percentage is an integer, not a rounding hazard.
- **Phone numbers** are stored E.164 (`+250781234567`) and always normalised by `phoneSchema` before write. Local form (`078 123 4567`) is a display concern only.
- **Enums** exist as PostgreSQL enums. The values in `packages/shared-types/src/enums.ts` mirror `schema.prisma` exactly; both change together, and the shared-types copy is what the API and clients validate against.
- **Soft deletion**: accounts move to `AccountStatus.DELETED` and financial rows are kept, because a refund query two years later must still resolve.

## Tables that authentication owns

| Table           | Purpose                          | Notes                                                                                                                              |
| --------------- | -------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| `User`          | identity, roles, status          | `phone` unique; `roles` is a PostgreSQL enum array; `passwordHash` exists but is null — this milestone authenticates with OTP only |
| `OtpChallenge`  | single-use codes                 | `codeHash` is `otp$<salt>$<sha256>`, never the code; `attempts`/`maxAttempts`; `consumedAt`, `invalidatedAt`                       |
| `Session`       | refresh tokens and devices       | `refreshTokenHash` unique (SHA-256 of the opaque token); `status`, `revokedReason`, `expiresAt`                                    |
| `ConsentRecord` | privacy consent                  | unique on `(userId, key, version)` so re-consent to a new version is a new row                                                     |
| `AuditLog`      | privileged and financial actions | `actorId` may be null (system actions), `entityType`/`entityId`, `before`/`after` JSON                                             |

Profiles (`CustomerProfile`, `RiderProfile`, `MerchantProfile`) are one-to-one with `User` and are created by the service for the roles that need them.

## Money and ledger tables (schema ready, features later)

`Payment` carries a **unique `idempotencyKey`** and a unique `providerReference`, so a retried collection cannot create a second charge. `PaymentWebhookEvent` stores the raw payload with a unique `(provider, providerEventId)` — a replayed callback is recognised rather than double-applied — and `signatureValid`/`processed`/`processingError` make reconciliation auditable. `Wallet.balance` is a projection; `WalletEntry` is the immutable ledger with a unique `reference`, and the balance is reconciled against the sum of entries rather than trusted on its own. `Refund` links to a payment with its own status machine.

None of these have endpoints yet. The tables exist now so that the booking and payment epics write into a schema that was designed for them instead of an afterthought migration.

## Applying the migration

```bash
pnpm run prisma:migrate:deploy     # prisma migrate deploy --schema prisma/schema.prisma
pnpm exec prisma migrate status --schema prisma/schema.prisma
```

Pooled connection strings (Neon `…-pooler`, Supabase `…-pooler`) are fine for `DATABASE_URL`. Migrations need a direct, session-pinned connection, so set `DIRECT_DATABASE_URL` to the non-pooled URL when using a pooler — `datasource db` in the schema already reads both.

**The application never migrates itself at boot.** Migrations run from a controlled deployment step (see `DEPLOYMENT.md`), because several instances starting at once against one schema is how a deployment turns into an outage.

## Keeping the migration honest

`pnpm run db:check-migration` regenerates the initial migration from `schema.prisma` with `prisma migrate diff --from-empty --to-schema-datamodel --script`, normalises trailing blank lines and CRLF, and compares against the committed file. It needs no database, so it runs inside `pnpm run verify` and in CI. When it fails, the fix is a new migration — not an edit to `0_init`.

## Seeding

`pnpm run db:seed` (`prisma/seed/seed.ts`) creates the accounts the auth and permission tests sign in as: one per self-service role plus the support, verification, finance and admin personas.

- It **refuses to run** when `NODE_ENV` is `production` or `staging`.
- It is idempotent: rows are upserted on the unique phone, so re-running updates instead of duplicating.
- Numbers come from `SEED_PHONE_PREFIX` (default `+2507880000`, two digits appended), so the operator decides which numbers exist.
- It writes **no** pricing, commission, service-area, booking or announcement data. Those are business decisions and must arrive through the admin API with an actor in the audit log. A seed that invented them would put fabricated production records in a live database.

## Testing against a real database

`pnpm turbo test:e2e --filter=@seremoto/api` needs a database whose connection string contains `test`; anything else is refused so a shared instance cannot be cleaned by a test run. CI brings up `postgres:16-alpine`, deploys the migration, seeds, and runs the journey. Each run picks a random six-digit phone tag, touches only its own numbers, and deletes exactly those rows and their OTP challenges afterwards.
